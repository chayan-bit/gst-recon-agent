# Real-world sanity split (`split = "realworld"`)

A small, hand-built eval set that answers "you trained and tested on your own simulator".
Every other eval set in this repo is generated by `gst_recon.sim` and rendered through `gst_recon/render/templates/`.
Here, nothing comes from the simulator except the rules engine that computes the expected output:

- **Documents** are printed through 7 invoice print formats published by real open-source accounting and billing software (ERPNext's GST app india-compliance, Odoo 18's Indian localisation, three Indian GST billing apps), not through our templates. See `PROVENANCE.md`.
- **Cases** (buyer, documents, purchase register, GSTR-2B, bank statement) are hand-written in `cases.json` and `parties.json`, not sampled by the simulator.
- **Ground truth** is computed by `gst_recon/sim/rules.py` from that structured truth, then compared with a hand-computed expectation per document (`expect` in `cases.json`, with the legal reasoning in `law`). The build refuses to render if they disagree.
- **Degradation**: none. Each PDF is rasterised at 200 dpi and read by Tesseract 5.5.0 with the repo's OCR settings ("clean scan" realism). Phone photos can replace 10 of the documents (`PHOTO_PROTOCOL.md`).

## Results so far

Truth target through the harness (oracle endpoint answering each case with its own `target.json`): composite 1.000, ITC invoice exact 1.000, context accuracy 1.000 (18 context documents), 0 errors.

Trivial baselines from `gst_recon.sim.audit` (handed the true extraction and links; keyword model trained on 2,000 simulator train cases), `python -m realworld.baselines --n-train 2000`:

| Baseline | ITC invoice exact | Context acc | ITC abs err (Rs) | Composite | GRPO | Ctx line acc |
|---|---|---|---|---|---|---|
| majority | 0.438 | 0.364 | 35,770 | 0.731 | 0.228 | - |
| no_anomaly | 0.486 | 0.364 | 34,202 | 0.747 | 0.231 | 0.481 |
| keyword | 0.424 | 0.318 | 21,201 | 0.739 | 0.366 | 0.407 |
| context_blind | 0.736 | 0.606 | 25,672 | 0.884 | 0.800 | - |
| rules engine (oracle) | 1.000 | 1.000 | 0 | 1.000 | 1.000 | - |

For comparison, on the simulator's test_iid split the same baselines score ITC invoice exact 0.673 (no_anomaly), 0.682 (keyword) and 0.790 (context_blind).
The real-world set is denser in anomalies by construction (most documents carry one), so trivial baselines score lower here; it is a coverage set, not a base-rate sample.
The keyword model, trained on simulator descriptions, does worse than "always eligible" on the real descriptions' context-dependent lines (0.407 vs 0.481): the simulator's surface forms do not transfer, which is what this split is meant to expose.

## How to run

    # truth + engine-vs-hand check (seconds, any machine)
    python -m realworld.truth                       # prints DISAGREE lines and exits 1 on any mismatch
    pytest tests/test_realworld.py

    # render, OCR, prompts (kratos: render venv, Tesseract 5.5.0, segno for the e-invoice QR)
    PYTHONPATH=$HOME/gst-rw-pylib:. GST_TESSERACT=$HOME/gst-tess/tesseract \
      ~/gst-recon-render/.venv/bin/python -m realworld.build --out data/realworld --truth-out data/truth/realworld

    # score a model; truth for context accuracy is found under data/truth/realworld
    python -m gst_recon.eval run --endpoint ... --model ... --cases data/realworld --out runs/eval/<name>-realworld --truth-dir data/truth
    python -m realworld.baselines --n-train 2000 --json runs/realworld/baselines.json   # usable as --baselines in eval report

    # phone photos (PHOTO_PROTOCOL.md)
    python -m realworld.build --images-dir photos/light1 --out data/realworld_photo/light1

`data/realworld/<case_id>/` has the usual `prompt.txt`, `target.json`, `meta.json`; `meta.json` adds per-document `format`, `delivery` (scan or photo) and `source` (upstream repo, licence, file, commit, method).
`data/realworld/print/` holds the rendered PDFs and `PHOTO_ORDER.txt`.

## Known limitations

- Small n: 12 cases and 36 documents. Use it as a sanity check with per-case reading, not for fine-grained comparisons; bootstrap CIs on 12 cases are wide.
- Real formats, synthetic parties: layouts, labels and print quirks come from real software, but every party, item, amount and GSTIN was written by us. The documents were not issued by real businesses.
- The printed layouts are produced by WeasyPrint with an approximation of each framework's CSS (frappe, Bootstrap, Odoo), not by the upstream application itself, and with the repo's bundled fonts (Liberation Sans, Kalam for the rupee sign).
- The surrounding inputs follow this repo's schema and renderers: the GSTR-2B JSON, the Tally-style register and the bank CSV are rendered by `gst_recon/render/tables.py`, the same code as for simulated cases. Only the invoices are out-of-distribution in format.
- Ground truth inherits the rules engine's documented simplifications (`gst_recon/sim/RULES.md`): for example, a credit note always reduces credit, the 180-day reversal is reported as deferred, IMS and s.17(2) apportionment are not modelled. The hand check found no case where the engine's output contradicts the law under those simplifications, but the hand expectations were written knowing them.
- Clean-scan realism only until photos are added: no blur, skew or lighting noise in the current build.
- No vendor marketing samples (Tally, Zoho, Vyapar, ClearTax) are included: none carried a reuse licence (`PROVENANCE.md`).
